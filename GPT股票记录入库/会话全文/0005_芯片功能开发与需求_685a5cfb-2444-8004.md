## 🔧 一、交换机的常见架构框架

从销售角度理解，一台交换机主要包含以下三个层次：

### 1. **硬件层（Hardware）**
- 芯片（如 Marvell AC5、Realtek RTL931x、Broadcom BCMxxxx）
- PCB 板（布线、电源、接口布局等）
- 接口模块（电口、电光混插、PoE 模块）
- 散热（风扇/铝片等）

- 哪个芯片支持几个千兆口/万兆口？
- 是否支持 PoE？最高功率？
- 工业级 or 商业级？防护等级？工作温度？

---

### 2. **固件层（Firmware）**
- 通俗理解：芯片“起作用”的基础软件，类似芯片上的“操作系统内核”
- 厂商一般会提供 SDK（软件开发包）或封装好的镜像文件
- 功能包括：MAC 转发、VLAN、STP、QoS、IGMP Snooping、PoE 控制等

👉 **销售建议理解要点**：
- 该芯片支持哪些 Layer2/Layer3 功能？
- 语音VLAN是否支持？
- IGMP Snooping、QoS、LACP是否齐全？
- 是否支持标准或定制 CLI 命令？

---

### 3. **软件层（Software/Application）**
- 指图形化管理、命令行界面（CLI）、Web、SNMP、API 等
- 可以接入 NMS 平台，如 UNMS、Cacti、Zabbix、SolarWinds 等

👉 **销售建议理解要点**：
- 有无 Web 配置界面？
- CLI 命令行是不是类 Cisco 风格？
- 是否支持远程 API 自动配置？（REST API、NETCONF、Ansible）
- 是否兼容主流 NMS 平台？

我给你写一个**简洁的 Python 示例**，展示如何通过 REST API 批量配置交换机端口的启用/禁用状态。  

假设交换机提供了如下的 REST API 接口：  

- **认证接口**：`POST /api/login` 传入用户名和密码，返回 token  
- **端口配置接口**：`PUT /api/ports/{port_id}`  
  请求体：`{"enabled": true/false}`  

下面是一个示例脚本：  

```python
import requests

# ========== 基本配置 ==========
BASE_URL = "http://192.168.1.100/api"   # 交换机 REST API 地址
USERNAME = "admin"
PASSWORD = "password"

# ========== 登录获取 token ==========
def login():
    url = f"{BASE_URL}/login"
    data = {"username": USERNAME, "password": PASSWORD}
    response = requests.post(url, json=data)
    response.raise_for_status()
    token = response.json().get("token")
    return token

# ========== 批量配置端口状态 ==========
def configure_ports(token, port_list, enable=True):
    headers = {"Authorization": f"Bearer {token}"}
    for port in port_list:
        url = f"{BASE_URL}/ports/{port}"
        payload = {"enabled": enable}
        response = requests.put(url, json=payload, headers=headers)
        if response.status_code == 200:
            print(f"Port {port} {'enabled' if enable else 'disabled'} successfully")
        else:
            print(f"Failed to configure port {port}: {response.text}")

# ========== 主程序入口 ==========
if __name__ == "__main__":
    token = login()
    # 例如：批量启用 1-4 号端口
    configure_ports(token, [1, 2, 3, 4], enable=True)
    # 例如：禁用 5-8 号端口
    configure_ports(token, [5, 6, 7, 8], enable=False)
```

- 这是一个通用示例，实际接口 URL 和 JSON 格式要参考 Marvell 或你设备的 API 文档。

## 1）先把“私有协议”列清楚（常见、会在客户清单/招标里出现的厂商专有协议）
> 说明：这里列的是**常见的厂商专有/非标准协议**，这些协议往往不属于 IEEE/IETF 公共标准，需要厂商额外实现或授权。

### **Cisco 相关（常见）**
- **CDP（Cisco Discovery Protocol）** — 设备发现，Cisco 专有（LLDP 为标准替代）
- **VTP（VLAN Trunking Protocol）** — VLAN 同步/分发（有安全/控制问题，常被替代）
- **HSRP（Hot Standby Router Protocol）** — Cisco 的主备路由协议（VRRP 为标准替代）
- **PAgP（Port Aggregation Protocol）** — Cisco 的链路聚合协议（LACP 为标准替代）
- **EIGRP（Enhanced Interior Gateway Routing Protocol）** — Cisco 的内部动态路由协议（专有）
- **UDLD（Unidirectional Link Detection）** — Cisco 光纤单向链路检测（有厂商实现类似功能）
- **Smart Install / SmartPort 等 Cisco 管理扩展**（某些自动化/发现/配置功能）

### **Cisco 起源但有厂商变体**
- **NetFlow**（最早由 Cisco 推广，后被多个厂商采纳、但实现细节/版本有私有扩展）
  - 许多厂商支持 NetFlow 或其变体（sFlow、IPFIX 等）

### **其他厂商/生态的专有协议**
- **Juniper**：J-Flow（NetFlow 变体）、一些私有管理扩展
- **Brocade / Extreme / HPE**：各自有历史私有管理/聚合扩展（名称多样）
- **厂商特定的 NMS/心跳/远程管理 协议**（某些大客户指定需要对接特定厂商NMS）

## 2）基于你采用 **Marvell AC5 系列**（出 PCBA）的情况 — 哪些功能 / 私有协议很可能**不被芯片/标准 SDK**原生支持（即需要额外固件或定制开发）

> 说明：不同ODM/固件栈（厂商在 Marvell SDK 上实现的功能）差别很大。下面列出根据你之前给文件与我们讨论中**常见缺口**（也就是你在招标需求里会碰到，但在 AC5 标准特性表或常见 SDK 实现中**常见不支持或弱支持**的功能）。这份清单可直接用作“向 Marvell/ODM 询问”的核对表。

### A. **厂商私有协议（通常不原生支持）**
- **CDP** — 通常 **不默认**，建议使用 **LLDP / LLDP-MED** 作为标准替代或要求 ODM 自行实现 CDP（需注意授权/兼容性）。
- **VTP** — 多实现厂商不默认支持（VTP 存安全隐患，本身并非推荐标准）。如果客户强制要 VTP，要明确 ODM 能否实现或建议改用集中化 VLAN 管理方案（REST API / NMS）。
- **HSRP** — Cisco 专有主备协议，芯片/SDK 通常不提供；标准替代是 **VRRP**（多数芯片/固件支持）。若客户坚持 HSRP，需要定制固件或告知使用 VRRP。
- **PAgP** — 链路聚合的 Cisco 私有实现，标准是 **LACP (IEEE 802.3ad)**，几乎所有 Marvell 平台支持 LACP，但 **PAgP 很可能不支持**。
- **EIGRP** — Cisco 专有路由协议，通常 **不支持**（若客户要求 EIGRP，需额外OSS/固件或推广使用 OSPF/RIP/BGP）。
- **UDLD / Smart Install / 其它 Cisco 管理扩展** — 大概率**不支持**，需评估是否必须。

### B. **动态路由 / 高级路由 / MPLS 类（AC5 系列常见限制）**
- **OSPF / IS-IS / PIM / BGP / MPLS / LDP / MPLS-TE / VRF**  
  - 许多中端交换 SoC（包括 AC5 的某些变体）**只提供静态路由和有限的 L3 功能**；高级动态路由（尤其 OSPF、BGP、MPLS、VRF）往往**不是芯片 SDK 的标准交付**，或只在更高端平台/特定 SDK 模块中提供。
  - **结论**：若客户需要完整 OSPF/BGP/MPLS 支持，必须在采购前向 Marvell/ODM 索要**功能矩阵**并确认固件支持，或选择更高端芯片/第三方 NOS（Network OS）。

### C. **面向管理/编排/自动化的现代接口（有时缺失或弱支持）**
- **NETCONF / YANG / RESTCONF / OpenConfig / gRPC** — 许多中端固件不自带这些现代化编排模型或只提供非常有限的 REST API。  
  - **结论**：如果客户强调“自动化/Ansible/NetOps”流程，必须要求 ODM/固件提供 REST API、或 NetConf/YANG 模型，明确 API 清单和示例代码（你要在报价/合同里写明）。
- **Telemetry（实时遥测）** — 部分 SDK 不支持推送式遥测（仅支持 SNMP 轮询）。若客户需高频遥测，需定制。

### D. **语音/视频类专用（AC5 常见短板）**
- **Voice VLAN 自动识别 / LLDP-MED 完整功能** — 在你之前的资料中 Voice VLAN 常被标注为缺失；LLDP-MED 在部分版本才支持。  
  - 若客户是 IP 电话/VoIP 密集型场景，要明确固件能否自动识别并打上 Voice VLAN，以及 QoS 策略自动下发能力。

### E. **高级隧道/安全功能**
- **IPSec VPN、GRE、DMVPN、IPSec 高级特性** — 中端交换芯片或许支持基础 GRE/IPSec，但**性能/加密能力/安全认证细节**会受限（如果客户需要高吞吐的加密隧道，需专门确认加密外挂或硬件加速方案）。
- **BFD / Graceful Restart** 等用于高速故障检测/路由恢复的高级协议：并非所有中端固件都有完整实现。

### F. **NetFlow / sFlow / 高级流量分析**  
- NetFlow 的某些专有版本或扩展字段可能**不完整**；但多数厂商会提供某种形式的 Flow 导出（sFlow / IPFIX / NetFlow），需看固件支持情况。
