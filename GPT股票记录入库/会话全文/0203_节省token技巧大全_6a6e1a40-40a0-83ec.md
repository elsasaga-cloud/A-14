Token 节省完整指南

一、理解 Token 消耗的本质

在给建议前先讲清楚成本从哪来，这样规则才不会死记硬背。

每次对话调用 = 系统提示 + 完整历史 + 当前输入 + 工具结果 + 输出，全部计入
历史消息每轮都会重新计费——不是只算新增的那部分，是整个对话累积重新过一遍
附件（文件、图片、搜索结果）一旦进入上下文，就和你手打的文字一样占空间
输出（回复长度）本身也是成本，不只是输入

理解这点后，规则的核心逻辑就是：减少进入上下文的无效信息量，减少重复传输，缩短对话生命周期。


二、通用法则

法则 1：信息密度优先

同样内容，选信息密度最高的表达形式。

结构化数据（表格/CSV/JSON）> 自然语言描述同样的数据
但反过来，逻辑/推理/说明性内容，自然语言反而比强行结构化（表格套表格）更省，别为了"看起来专业"过度格式化

法则 2：视觉 vs 文本，按"信息是否天然视觉化"决定

不是"图片都费token所以别用图"，而是：

图表、UI截图、手写笔记、照片——这些信息离开视觉就丢失语义，该用图就用图，因为让我"猜"文字反而更容易出错，返工更贵
一段文字内容如果被截图发送（比如聊天记录截图、代码截图）——这种优先转文字，因为图片没有比文字承载更多信息，纯粹是浪费

法则 3：上传文件 > 粘贴内容（大文件场景）

上传的文件我可以按需读取（比如只读某几行、某个sheet），而粘贴进对话框的内容是全量强制进入上下文，没有选择权。数据越大这个差距越明显。

法则 4：让我做"选择性阅读"，而不是你做"预处理喂给我"

反直觉的一点：与其你自己先把大文件精简好再贴给我（人工操作成本高、还可能删掉关键信息），不如整份上传，让我用工具去定位、提取、处理——我读取文件本身如果通过代码执行，不一定全部进 token 上下文。

法则 5：任务拆分 vs 一次性大任务

需要多轮反复修改的大任务（改文档、写代码），用 artifact 或文件方式协作，而不是每次都让我完整重复输出全文再让你复制
增量修改远比整体重发省

法则 6：对话要"新陈代谢"

单个对话不要无限延续。一旦主题切换或历史已经很长且和当前任务不再强相关，开新对话
需要延续上下文的，可以让我先做一次总结，用总结起新对话，而不是把整个历史拖过去

法则 7：一次问清楚，减少来回试探

模糊问题会导致"追问-澄清"的多轮消耗，每轮都是完整历史重传
尽量一次把约束、目标、格式要求说清楚，即使问题本身变长了，也比来回五轮划算

法则 8：明确输出长度和格式要求

不设限时，我可能会给出偏长的解释、示例、免责声明
如果你要的是"结论"而不是"过程"，直接说"只要结论""控制在N字以内""不要例子"——输出token也是成本，而且是双向的（我生成的也要计入这轮上下文，供你下一轮用）

法则 9：搜索/工具调用要克制

每次网页搜索的结果本身会作为内容进入上下文，一次宽泛模糊的搜索可能拉回大量无关内容
问题越具体，搜索词越精准，返回的无效信息越少

法则 10：避免"重复确认式"对话

不需要每一步都让我复述你已经说过的内容再确认，这类"复读"是纯浪费
需要复核时，指向"差异点"而不是要求完整重述全文


三、格式选择速查表

内容类型 推荐格式 避免
表格数据 CSV/TSV，或直接上传 xlsx 表格截图
长文档 上传 md/txt/docx，让我按需读 全文手动粘贴进对话框
代码 直接贴代码块或上传文件 代码截图
图表/设计稿 图片（必要） 用文字描述图表内容(容易失真且更啰嗦)
聊天记录/网页文字 转文字/markdown 截图
扫描件/手写 图片（必要，OCR类需求） —


四、一个容易被忽略的点

省 token 不等于极简主义。有时候为了省 token 故意压缩信息、跳过必要上下文，反而导致我理解错、答错，你要花更多轮次纠正——总成本更高。真正的优化目标是**"用最少的冗余，把必要信息一次说清楚"**，而不是"信息量越少越好"。

> 少给AI信息。

> **用最低 token，把最高价值的信息送进去。**

可以理解为：

```
普通用户：
大量原始信息
        ↓
AI筛选

高手：
结构化信息
        ↓
```

AI最擅长的是：

**思考、总结、生成、比较。**

把信息整理成机器友好的形式，你和 AI 的效率会提升一个数量级。你目前的使用方式（Saga、代码、投资框架、SEO）其实非常适合采用这一套。
